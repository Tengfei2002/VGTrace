一、先读取仓库，确认当前发布流程
1. 通过已连接的 GitHub 工具或仓库工作区读取当前默认分支、README、package.json、.github/workflows/pages.yml、.github/workflows/deploy-pages.yml、.github/workflows/save-collections.yml 和最新提交。当前发布工作流是推送 main 后运行 npm test、npm run build、npm run check，并由 GitHub Actions 发布 dist 到 GitHub Pages；收藏通过独立的 Issue／Actions 流程写入 collections 分支，保存成功后复用deploy-pages.yml工作流发布静态收藏快照。执行时以仓库实际文件为准。
2. 读取 data/manifest.json、data/meta.json 和清单中全部 data/games-*.json；页面源文件在 src/template.html、src/client.js、src/bootstrap.js。不要只编辑生成的 dist 文件。
3. 如果无法读取或写入目标仓库，明确说明缺少的访问能力并请求正确仓库链接或授权。不要假装已提交，也不要另建同名仓库、改写无关仓库或用下载文件冒充仓库更新。
4. 保留当前布局、稳定游戏 key、原有条目、收藏存储键及全部功能；先检查工作区和远程分支，保留用户未提交的改动，不强制推送、不覆盖他人提交。

二、多来源查漏与事实核对
1. 优先覆盖最近90天新作、最近一年热门或高评价作品，以及2019年至今遗漏的常玩作品。至少采用三种独立发现路径：Steam热门新品／热销／最多游玩榜，Nintendo Switch／Switch 2官方目录与公告，PlayStation／Xbox官方目录，以及开发商或发行商官网。不能只补点名作品，不设固定收录上限。
2. 先列候选，再按Steam AppID、其他平台稳定ID、名称和平台代际查重。辨别同名重做、重制、移植、合集和独立DLC；不能合并不同作品，也不能重复计算跨平台版本。试玩、原声、工具和普通附加内容不当作完整游戏。已取消移植计划不算实际平台。
3. 区分正式发行、抢先体验、未发行和下架／停服。Demo、预购或提前解锁不能自动当作正式发行；未发行作品只能留在明确标记的关注／待办中。历史条目保留，不承诺仍在售或联机服务有效。
4. 公开数据集及SteamDB、IGDB、RAWG、OpenCritic、Metacritic可作发现或交叉核对。需要密钥、被拒绝或连接失败的来源如实记录；优先批量读取允许访问的Steam文字元数据，不绕过访问限制、不伪造接口返回。
5. 每条新增事实至少记录常用名称、开发商、发行商、主要玩法、原始标签、具体平台代际、来源版本日期、发行状态、推荐理由、适合人群、时长依据、原始来源链接和本次核验日期。来源仓库更新日、读取日、逐条采集日和网页缓存日期要区分。未知厂商、分级、价格、评分、时长和平台支持留空或标未知。
6. Steam评论必须注明语种、购买来源、过滤方式和样本日期；不把单语好评率冒充全语种，不将旧快照写成实时数据。主机评分与Steam好评率分开。
7. 时长优先使用可核验的逐款社区数据，并注明主线／主线加额外内容／全收集及样本日期；旧归档不能写成最新实测。缺少数据时保留明确标注的编辑估算或类型预算。长期游戏给出建议投入和单局时间，不伪造通关时长。

三、保留内容和交互要求
1. 背景／大致玩法简介覆盖至少90%，保留来源与语言，尽可能批量补齐；不得用重复的通用模板冒充逐款简介，不剧透结局。
2. 中文名只用已有官方名称或有明确依据的常用名，不机翻英文游戏名；英文更常用的保留英文主标题，已有中文名仍可搜索。
3. 保留搜索、组合筛选、排序、卡片／表格、随机推荐、CSV导出、收藏及备份恢复和底部维护提示词。保留已通关、正在游玩、计划中、未游玩、已弃坑五种收藏状态及计数；收藏页不展示探索筛选栏，主页五状态复选框按或关系筛选。version1备份兼容归入未游玩，version2保留状态。
3a. 保留0731和0425两套独立收藏档案、每次打开的一次点击选择、界面切换、切换前保存提醒、只读查看对方、当前用户云端保存和读取。收藏上传按钮保留在导出结果左侧，同时支持CSV与原JSON；JSON上传与下载使用原version2格式并兼容version1。CSV兼容当前导出与旧编号格式，新导出保留稳定游戏标识和Steam AppID；按五状态导入，空状态跳过、不删除收藏，未匹配或重名歧义要报告，异常状态或重复冲突不能静默写入；上传只合并当前用户，本机旧存储不覆盖，迁移前留快照并由用户选择归属。
3b. 云端收藏唯一来源是collections分支中的collections/0731.json与collections/0425.json；main内同名初始文件不能用于覆盖实际收藏。日常游戏维护不得重置、覆盖、合并或强推该数据分支。保留GitHub确认一次后由Actions保存的流程、作者权限与格式校验、直接替换当前用户云端文件（不因客户端旧SHA拒绝）、后台并发重试、可选读取合并、本机草稿和真正收到云端结果才确认成功的规则，浏览器只读取同源cloud-collections.json，不恢复GitHub REST API读取。保留请求合并、短缓存、手动刷新和保存确认的强制更新及失败退避；快照必须读取真实collections分支的同一提交及准确blob SHA，不用main空示例。保存无需人工审查Issue；保留失败请求自动重试及保存后自动发布快照的可复用工作流，不加入个人令牌或收费后端；公开仓库存储的收藏不承诺私密。
3c. “我的收藏”和“分类总览”隐藏维护提示词模块；其他原有入口保留，不新增游玩日期轨迹、画廊或甘特图。
4. 不恢复侧栏的年份范围、推荐分组、发行状态、Steam商店年龄门槛四个筛选控件；字段可保留在详情和导出。综合推荐用统一排序，不将点名作品固定置顶。来源放原有“来源与方法”和详情，不另加显眼来源宣传模块。
5. 明确支持双人的作品同时保留多人标签，逐款记录具体模式和人数依据；不能仅凭合作标签推断全游戏只限两人。区分原生Switch 2版本与兼容运行，不把升级包重复计数。
6. 保留成年分级及来源含裸露／性内容标签的游戏。普通作品只提示来源内容标签；不要逐款展示“未归入黄油分组”。required_age与ESRB／PEGI／CERO分开，0或缺失不表示全年龄。18+、暴力、单一裸露标签、截图或整个系列名称都不能直接决定成人向核心分组。
7. 黄油／成人向是独立、可交叉的内容分组，保留原玩法和专区入口，专区按题材、玩法、厂商、内容属性筛选。卡片、详情、表格和CSV均逐款保留：扮演谁（姓名／职业／处境，来源未知则说明）、具体怎么玩（实际操作与推进循环）、成人内容体现（角色事件、CG、动画、去衣、画廊、互动等非露骨内容形式）。保留基础版、补丁和版本差异及依据；不补造人物年龄、情节或具体场景。误归入普通作品时只修正分组，保留游戏。

四、直接更新仓库并通过现有工作流发布
1. 修改仓库中的游戏分片、manifest、meta、页面源文件及必要的构建脚本。同步总数、分类／平台／年份统计、简介覆盖、动态选项、推荐分组和更新时间。保留相对资源路径，确保 /VGTrace/ 子路径正常；不加入必需的第三方前端服务或API密钥。
2. src/maintenance-prompt.txt 是维护提示词模板；data/meta.json 中 maintenancePrompt 是解析后的网页文本，maintenancePending 是待办数据。同步模板、实际文本和待办，运行构建，不能只在聊天里给一份新提示词。
3. 先获取最新collections远程分支，再执行 npm test、npm run build 和 npm run check，检查总数、稳定key与AppID唯一性、字段类型、日期、链接、未知值和所有分片完整性；实际测试几个新作检索、平台／玩法／时长组合、双用户收藏隔离与只读查看、备份上传下载、冲突和保存确认、CSV、提示词复制与TXT一致性。浏览器不可用时明确说明已做的检查及未做的视觉验收。
4. 检查提交差异，只提交与本次维护有关的源码和游戏数据。按仓库现有规则提交并推送；允许直推main时正常提交，分支保护要求PR时创建分支和PR，遵守既有合并规则。不要 force push，不提交凭据、私密截图、缓存和无关文件；不把个人收藏混入游戏维护提交。用户明确发起的收藏保存仅通过专用流程写入collections分支。
5. 推送后检查与本次提交SHA对应的 Publish VGTrace 工作流和部署结果。工作流失败时读取日志并修复；失败未解决则保留待办并报告。PR未合并、提交未推送、Actions未成功或站点未验证，均不能称为“已更新线上网站”。
6. 默认交付仓库提交／PR链接、Actions结果、实际网站地址及简要变更说明。完成标准是仓库修改已保存且发布状态清楚；不以生成、下载或返回一份独立HTML文件作为本次任务交付。
